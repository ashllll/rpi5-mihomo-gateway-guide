# 网关-1053静默

> **触发**：家里设备突然上不了网但 ping 网关正常；mihomo 进程在、TUN 在、`business=verified`，只有客户端 DNS 坏了。
> **验证**：`mihomo-healthcheck --state` 里 `dns_1053=ok` 且 `business` 不是 `failed`；`dig @127.0.0.1 -p 1053 example.com A +tcp` 有 198.18/198.19 答案。

## 首选

```sh
dig @127.0.0.1 -p 1053 www.baidu.com A +notcp +time=2 +tries=1
dig @127.0.0.1 -p 1053 example.com A +tcp +time=2 +tries=1
mihomo-healthcheck --state   # dns_1053 / dns_fail_streak / reason / last_restart_reason
```

连续 3 个定时样本失败才判 `business=failed`（一个域名抖动不算）；healthcheck 与 dnsmasq-guard 都会在预算内重启 mihomo，guard 保留 `dns-path-down`/`resolver-silent` 告警。

## 被挡时

`systemctl status mihomo` 看到 `start request repeated too quickly`：等 healthcheck 的 `reset-failed` + 单次重试；每 boot 最多 2 次，之后 `reason=start-limit-blocked`，要人工看配置。

## 别再来

| 弯路 | 为什么不通 |
| --- | --- |
| 只看 `systemctl is-active mihomo` 就判 DNS 好 | 1053 监听可以静默，进程/TUN/出口探针全绿 |
| 只查一个域名 | 单域名上游抖动会误重启，连续 3 次 + 双域名双传输才准 |
| 失败一次就立刻重启 | 会拉断所有长连接；连续 3 个样本、每小时一次、成功才清冷却 |
| 用 `restarted_at` 当冷却 | 尝试前写入会在瞬态失败后锁死约 61 分钟；应分 `restart_attempted_at` / `restart_succeeded_at` |

## 注意

- 探针查的是客户端真实路径（127.0.0.1:1053，UDP 与 TCP 都要过），不是 mihomo 的内部解析。
- 订阅验收用更严的门：国内域名 + fake-IP 域名各一，UDP/TCP 全过才接受新配置。

证据：F-21/F-22 提交；`tools/check_client_dns.py`、`tools/check_stability.py`。
