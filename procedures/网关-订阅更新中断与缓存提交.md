# 网关-订阅更新中断与缓存提交

> **触发**：更新失败缓存被污染；SIGKILL 后维护锁不释放；相同配置强制更新失败但未恢复。
> **验证**：实际 CLI 故障注入后，配置、缓存、进程操作和持久记录符合提交阶段，不能只看退出码。

## 首选

`python3 tools/check_update_transaction.py && python3 tools/check_subscription_update.py`

## 被挡时

- 先用合成配置与真实文件锁测 CLI；Linux 上复验进程组、fsync 和 systemd 边界，不在生产停核心注入故障。
- 现场源码比仓库新时逐项核对：primary/extra 规范化入口和 restart 语义必须保留；普通 Clash fixture 不能覆盖 base64/URI。

## 别再来

| 弯路 | 为什么不通 |
|---|---|
| 验收前晋升缓存 | 坏来源覆盖最后可用缓存，回滚失去干净输入 |
| 已 accepted 后因缓存失败回滚核心 | 把已工作的网络再次打断；应保持核心、恢复旧缓存并保留待恢复记录 |
| 只杀 timeout 的直接子进程 | 孙进程还能晚写；命令替换的父 shell 也不等于事务 owner |
| prepared 且当前 hash 等于旧 hash 就清记录 | --force 可让新旧 hash 相同，核心仍可能已重启失败 |
| 仅 HTTP 状态码匹配就验收 | curl 失败也可能已经输出 200/204，必须同时检查退出状态 |

## 注意

- 持久 accepted 是提交点；快照先 fsync，缓存晋升落盘后才清 pending，目录同步不能遗漏。
- owner 用 PID 和启动身份识别，僵尸态视为死亡；子进程组退出、延迟写入及双锁可重取都要实际验证。
- pending 在下次调用本地恢复后退出，不宣称断电后自动开机恢复已验收。

证据：2026-10-29 本地 hardening 交付目录的 `validation/updater-review.md` 与最终 Linux CLI 记录；上述两项仓库回归。
