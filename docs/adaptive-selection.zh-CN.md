# 智能节点选择：设计与边界

本文描述已发布的实现与它的边界。可执行部分在
[`automation/`](../automation/README.zh-CN.md)：`mihomo-adaptive-score` 只做影子评分采集，
`mihomo-adaptive-apply` 只在门禁满足时执行隔离，`mihomo-policy-overlay` 依据能力清单生成分组。
节点标签、阈值与供应商能力数据是部署数据，不随仓库发布。

## 当前稳定性策略

`capabilities.yaml` 的 `stability.groups` 可覆盖业务组的探测参数，公开模板为 AI、X、Telegram、
YouTube 设置 45 秒主动检测，Auto 为 60 秒。节点成员与供应商能力限制保持独立。
`stability.telegram_cidrs` 保存 Telegram 官方公布的网段，规则在域名规则前匹配 IP 直连客户端。

健康检查每分钟并行测试业务，只对失败的业务组发起带期望状态码的复测；进程仍在运行时，
不因为单业务异常重载或重启整个 Mihomo。进程未运行时保留重启恢复。
影子评分必须检查 `extra[url].alive`：部分核心在 HTTP 状态不匹配时仍返回非零延迟，不能仅凭数字判健康。

ChatGPT 网页 GET 与 OpenAI API 分开检查。网页 403 标为 `restricted`，连接失败标为 `unreachable`，
不把 API 复测宣称为网页恢复。命令行受到网站验证时，应再用真实浏览器 / App 验收。

默认 timer 集合不启用 `mihomo-adaptive-apply.timer`，避免隔离执行频繁热加载全配置。
升级既有部署时保留原有 timer 状态，需人工停用旧执行 timer；manifest 也需合并新字段。
45 秒只是检测周期，不保证固定恢复时间或长期零断连。

## 先筛能力，再比较质量

每个供应商和节点用配置描述 allowed_services、download_allowed、region、
metered 和 enabled。先排除不允许承载该业务的节点，再评分；禁止用最低延迟覆盖能力限制。
AI 池、普通浏览池、下载池互相独立。供应商原始订阅和分组保留，覆盖规则另存，
更新时不要把供应商配置就地改成不可恢复的新版本。

## 指标与评分

按业务分别记录最近成功率、连接时间、TLS / 首字节耗时、抖动、失败连续次数及样本年龄。
延迟使用指数滑动平均，失败要增加惩罚；过期样本不当作健康证明。
下载吞吐只能通过授权下载节点的有上限小文件采样补充，且设置每轮流量和并发预算。
通用 generate_204 只能证明轻量连通性，不能证明 AI 会话、YouTube 播放或模型下载速度。
HTTP 401 可以证明无凭据 API 请求到达服务，但不能证明用户账号已登录或可完成对话。

建议评分为可配置加权值，权重按交互、流媒体、下载分别定义，不公开固化所谓最优常数。
节点类型、供应商额度、地区政策和采样可信度应是评分输入，不能从节点名猜全部能力。

## 隔离与恢复

```text
采集 → 更新业务指标 → 能力过滤 → 连续失败门槛
  → 影子决策 → 保底候选池检查 → 备份候选配置
  → 语法验证 → 有限应用 → 分类业务验证 → 保留或回滚
```

一次失败只记录；连续失败才进入隔离，且必须保留每个业务池的最少候选数。
上游本身故障时暂停节点惩罚，避免把所有机场误判为坏节点。
恢复节点经过冷却和连续成功观察后逐步加入，避免立即反复切换。
采集、订阅更新、隔离执行应共用协调机制，避免相互覆盖配置。

## 会话与下载

AI 优先同地区、稳定出口，并设置切换收益门槛、保持时间和故障冷却。
切换不能迁移已有 TCP / WebSocket 会话，禁止为追求更低几毫秒频繁断开长连接。
load-balance 是在连接间分配，不是把一个 git clone 或单文件流聚合成多机场带宽。
多连接下载由支持分块的客户端实现，需遵守供应商限制和源站能力。

Git clone 的大数据和网页控制可能使用相同 github.com 主机，不能仅靠
codeload / LFS / releases 的独立域名规则覆盖全部 Git 大流量。必要时在终端为 Git
显式选择下载代理入口，而不是承诺网关能够识别 HTTPS 内的所有内容。
